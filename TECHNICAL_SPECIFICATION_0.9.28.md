# ESDS 0.9.28 — техническое задание: полноценное управление библиотекой

## 1. Цель

Доработать ветку `vibe/palette-library-management-66d870` (0.9.27), сохранив её функциональность и исправив проблемы управления личной библиотекой. Результат — устанавливаемая сборка Obsidian-плагина для Android/Desktop, а не демонстрация или GitHub Preview.

Палитра остаётся в режиме **Single Mode**: один фиксированный набор цветов, не переключающийся вслед за светлой/тёмной темой Obsidian. Возвращать разделение Light/Dark для палитр нельзя.

## 2. Типы элементов и независимость данных

Библиотека состоит из трёх независимых типов:
- **Палитры** — `palettes`, категория `categories.palettes`.
- **Фоны заметок** — `backgrounds`, категория `categories.backgrounds`.
- **Стили информационных блоков** — `blockStyles`, категория `categories.blockStyles`.

Идентификаторы и названия проверяются в пределах своего типа. Совпадение названия палитры с названием фона или стиля не является дубликатом и не должно блокировать импорт, создание или переименование.

## 3. Единая политика совпадений и дубликатов

### 3.1. Общее правило
Ни один корректный элемент нельзя молча пропустить только из-за совпадения ID или названия. По умолчанию система сохраняет все корректные элементы и автоматически назначает конфликтующему элементу уникальные имя и ID.

Пример:
- `Mango Sunrise`
- `Mango Sunrise (2)`
- `Mango Sunrise (3)`

Алгоритм должен учитывать регистр, пробелы по краям и уже существующие суффиксы. Он обязан находить следующий свободный суффикс, а не перезаписывать существующий элемент.

### 3.2. Где политика обязательна
Проверка и автоматическое переименование применяется во всех подходящих операциях:
- создание палитры, фона и пользовательского стиля;
- редактирование/переименование существующего элемента;
- дублирование любого типа элемента;
- одиночный JSON-импорт;
- пакетный импорт нескольких JSON;
- ZIP-импорт коллекции;
- импорт общего файла `esds-export`;
- импорт полного дизайнерского набора;
- создание и переименование категорий.

При переименовании существующего элемента он исключается из проверки собственных имён, чтобы сохранить своё текущее название без ложного конфликта.

### 3.3. Поведение интерфейса
Пользователь должен получать ясное сообщение, если название автоматически изменено. Сообщение показывает итоговое имя. Для выбора категории пользователь может:
- выбрать существующую категорию;
- создать новую;
- если введённое название занято — создать новую категорию с автоматически подобранным уникальным названием.

Система не должна молча переключать пользователя на уже существующую категорию вместо создания запрошенной новой.

### 3.4. Ошибки и пропуски
Совпадения имён/ID не считаются ошибкой импорта и не увеличивают счётчик пропусков. Пропускать можно только повреждённые или неподдерживаемые записи; они должны быть посчитаны отдельно и сопровождаться понятной причиной. Если все записи невалидны, импорт должен завершиться с ошибкой без потери прежней библиотеки.

## 4. Управление категориями

Для всех трёх типов в едином стиле должны поддерживаться:
- создание;
- переименование;
- удаление с переносом элементов в безопасную категорию;
- перемещение категории выше/ниже;
- выбор существующей категории;
- создание новой категории непосредственно в сценарии перемещения;
- автоматическое разрешение совпадения имени категории;
- синхронизация текущего выбранного фильтра после переименования;
- сохранение и восстановление предыдущего состояния при ошибке записи.

Меню управления категорией `⋯` должно быть доступно на плитках категорий палитр, фонов и стилей блоков, а не только в одном разделе.

Системные/защищённые категории не должны получать действия удаления/переименования, если это противоречит их флагу `protected`.

## 5. Управление элементами библиотеки

Для пользовательских элементов всех применимых типов:
- просмотр и применение;
- переименование;
- перемещение между категориями;
- дублирование с уникальными именем и ID;
- экспорт JSON;
- удаление с подтверждением;
- корректное обновление избранного и активного выбора;
- корректная обработка ошибки сохранения с откатом.

Для палитр дополнительно:
- редактирование цветовых ролей и параметров палитры;
- изменение порядка внутри категории.

Для фонов и стилей блоков действия переименования, перемещения, дублирования и удаления должны быть доступны в каталоге так же явно, как для палитр.

## 6. Массовые операции

Массовый режим должен работать независимо для текущего типа элементов и поддерживать:
- выбор отдельных карточек;
- выбрать всё;
- снять выбор;
- массовое перемещение в существующую или новую категорию;
- массовое удаление с подтверждением;
- экспорт выбранного в ZIP;
- экспорт выбранного в один JSON.

После смены типа, смены категории, перехода назад из категории, изменения поискового запроса или выхода из массового режима устаревшее выделение должно сбрасываться. Счётчик должен соответствовать только текущему видимому контексту.

Нельзя допускать, чтобы невидимые из-за поиска или смены категории элементы оставались выбранными и попадали в массовое удаление/перемещение.

## 7. Импорт и экспорт

Поддерживаемые форматы:
- отдельный JSON палитры;
- отдельный JSON фона;
- отдельный JSON стиля блоков;
- общий JSON `type: esds-export`;
- ZIP-коллекция с JSON-файлами и манифестом;
- полный дизайнерский набор `esds-theme-pack`.

Требования:
- импорт одного типа не сравнивает названия с другими типами;
- корректные совпадающие элементы сохраняются под уникальными именами;
- повторяющиеся ID получают новые уникальные ID;
- порядок элементов в пакетном файле сохраняется;
- ошибки отдельных файлов показываются отдельно от автоматически переименованных совпадений;
- пакетный импорт не должен заменять всю библиотеку, если пользователь явно не выбрал операцию восстановления/замены библиотеки;
- ZIP-экспорт включает каждый выбранный элемент и манифест с типом, количеством, категориями и датой экспорта;
- JSON/ZIP сохраняются в папку Obsidian `ESDS Exports`.

## 8. Сохранение и целостность данных

- Все изменения сохраняются через штатный `saveUserLibrary()`.
- При неудачном сохранении операция должна сообщить об ошибке и восстановить предыдущее состояние данных.
- Нельзя удалять или перезаписывать другие типы элементов из-за совпадающего ID/названия.
- Избранное должно очищаться только для реально удалённого элемента соответствующего типа.
- Активные палитра/фон/стиль должны переключаться на безопасное значение при удалении активного пользовательского элемента.
- Импорт не должен частично и незаметно портить библиотеку.

## 9. Android и интерфейс

- Не использовать `window.prompt()`: текстовый ввод должен идти через модальное окно, совместимое с Obsidian/Electron/WebView.
- Кнопки и меню должны иметь удобные сенсорные области.
- Категорийные меню и массовая панель должны переноситься на узком экране.
- Длинные названия не должны ломать карточки и модальные окна.
- Не использовать hover как единственный способ доступа к функции.
- Действия должны быть доступны нажатием на Android.

## 10. Проверка перед выдачей сборки

Обязательные статические проверки:
1. `node --check main.js`.
2. Проверка JSON-синтаксиса `manifest.json` и `versions.json`.
3. Поиск прямых вызовов `window.prompt(`.
4. Проверка, что старые сообщения о пропуске дубликатов больше не используются для конфликтов имени/ID.
5. Проверка независимости имён для палитр, фонов и стилей.
6. Проверка, что управление категориями присутствует у всех трёх типов.
7. Проверка, что массовое выделение очищается при поиске и смене категории.
8. Проверка содержимого ZIP-архива и установочной структуры плагина.

Ручной запуск в Obsidian Android должен быть обозначен отдельно от статических проверок. Нельзя утверждать, что Android runtime проверен, если плагин реально не запускался на устройстве.

## 11. Поставка

- Исходная база — ветка `vibe/palette-library-management-66d870`.
- Работы выполняются в отдельной ветке, не изменяя исходную ветку и `main`.
- Версия результата: `0.9.28`.
- Ветка должна содержать полный комплект исходников плагина.
- Для установки пользователь получает ZIP репозитория по отдельной ветке. В архиве должна быть папка плагина с `main.js`, `manifest.json`, `styles.css` и всеми необходимыми файлами.
- Никаких обязательных GitHub Preview, публикации релиза или слияния в `main` не требуется.

## 12. Критерий готовности

Задача готова, когда все перечисленные функции реализованы в исходниках, статические проверки пройдены, отдельная ветка создана, а ZIP по прямой ссылке доступен для скачивания. Непроверенные сценарии Android runtime должны быть явно перечислены.
